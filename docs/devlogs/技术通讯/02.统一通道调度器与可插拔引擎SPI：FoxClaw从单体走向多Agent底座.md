# 统一通道调度器与可插拔引擎 SPI：FoxClaw 从单体走向多 Agent 底座

> 记录 FoxClaw 从单一 Codex 专属桥接器，演进为支持 Codex、OpenCode 与 Google Antigravity 多引擎并行的统一 Agent 调度底座的架构重构全过程。

---

## 1. 演进背景：为什么“给新 Agent 复制一套桥”走不通

FoxClaw 最初的诞生，是为了解决自管本机 Codex 的最后一公里：在离开电脑时，通过受信任的 Telegram / 微信移动端入口完成审批接管、线程观察、多账号轮转与跨节点同步。

在最初的单体架构下，整个系统以 Codex 的 `app-server` JSON-RPC 协议与状态机为绝对中心：
- 会话轮次（Turn）的并发控制紧耦合在 Codex 的 RPC client 回调中；
- Telegram 消息流式编辑、工具执行折叠、长文本分块等交互逻辑直接混杂在 `TelegramBotController` 内；
- 崩溃恢复、异常捕获与队列状态紧密依赖单一 Codex thread 机制。

当系统进一步引入支持多模型的 OpenCode，以及 Google 最新的 Antigravity (`agy`) 深度编程 Agent 时，一个严重的架构矛盾暴露在眼前：

如果为每个新 Agent 各自编写一套 Telegram 桥接控制器，整个工程将迅速陷入“代码爆炸与维护灾难”：
1. **交互逻辑严重冗余**：Markdown 富文本转义、700ms 节流流式编辑（Telegram 429 规避）、长消息（4000 字符）安全切分、工具调用块折叠（`<blockquote expandable>`）、活跃态 Typing 维持等通用交互在各个控制器中反复重抄（单是 Antigravity 控制器最初就复制了近 900 行交互代码）；
2. **调度行为难以统一**：各个 Agent 面对瞬时并发请求时的行为不一致，有的在内存中丢弃，有的挂起阻塞，缺乏统一的抢占、队列与重启自愈保障；
3. **运维与状态观测割裂**：指令体系如 `/setup`、`/status`、`/models`、`/effort`、`/steer`、`/interrupt` 在各个 Agent 之间表现各异，账号候选池与配额展示缺乏标准抽象。

“重构吧，架构很重要。多花点精力没毛病。”

这是一次必然的系统升级。FoxClaw 决定重塑内核，拆分核心责任：将**与渠道无关的会话调度、流式预览、消息切分、交互折叠与队列恢复**下沉为通用的 `UnifiedChannelOrchestrator`；将**与具体模型/引擎相关的执行交互、鉴权生命周期与参数控制**抽象为标准化的 `IEngineAdapter`（Engine Service Provider Interface）。

## 2. 架构设计：两层模型与分工契约

重构后的 FoxClaw 采用分层解耦架构：

```
                ┌────────────────────────────────────────────────────────┐
                │             Telegram / 微信 / 移动端渠道层              │
                └───────────────────────────┬────────────────────────────┘
                                            │
                                            ▼
               ┌─────────────────────────────────────────────────────────┐
               │         UnifiedChannelOrchestrator (统一通道调度器)       │
               │  - Turn 抢占与并发排队 (TurnQueue)                       │
               │  - 700ms 智能节流流式预览 (StreamPreviewController)       │
               │  - 消息分块 (chunkTelegramMessage) 与富文本安全转义      │
               │  - 工具调用过程动态折叠 (<blockquote expandable>)        │
               │  - 服务崩溃/重启后的队列中断与自愈恢复                      │
               │  - 统一通用命令分发 (/setup, /status, /steer, /interrupt) │
               └────────────────────────────┬────────────────────────────┘
                                            │
                           Engine SPI (IEngineAdapter)
                                            │
         ┌──────────────────────────────────┼──────────────────────────────────┐
         ▼                                  ▼                                  ▼
┌──────────────────┐               ┌──────────────────┐               ┌──────────────────┐
│  Codex Adapter   │               │ Antigravity Adp  │               │ OpenCode Adapter │
│ (App-Server RPC) │               │ (CLI ChildProc)  │               │ (HTTP Streaming) │
└──────────────────┘               └──────────────────┘               └──────────────────┘
         │                                  │                                  │
         ▼                                  ▼                                  ▼
   Codex Runtime                  Antigravity Engine                  OpenCode Engine
```

### 2.1 引擎服务提供者接口（Engine SPI）

在 `src/core/engine_spi.ts` 中，我们提炼了面向 Agent 运行时的最小完备接口：

```typescript
export interface IEngineAdapter {
  readonly id: string;
  readonly displayName: string;

  executeTurn(
    request: EngineTurnRequest,
    callbacks: EngineTurnCallbacks
  ): Promise<EngineTurnExecution>;

  cancelTurn(turnId: string, runId?: string): Promise<boolean>;

  buildStatusSummary(): Promise<string>;
  buildSetupKeyboard?(): Promise<{ text: string; reply_markup?: any }>;

  handleCommand?(command: string, args: string[], ctx: EngineCommandContext): Promise<boolean>;
  handleAction?(action: string, ctx: EngineActionContext): Promise<boolean>;

  resolveCurrentModel?(): Promise<string | null>;
  resolveCurrentEffort?(): Promise<string | null>;
  switchModel?(modelId: string): Promise<void>;
  setEffort?(effort: string): Promise<void>;

  handleTurnError?(context: EngineTurnErrorContext): Promise<string | null>;
  onTurnComplete?(turnId: string): Promise<void>;
}
```

任何接入 FoxClaw 的后端 Agent，只要实现该接口，就能立刻获得：
- 零代码成本获得防抖、防限流的流畅流式打字输出；
- 完整的工具调用过程折叠；
- 命令排队、插队、打断与重启自愈；
- 标准的移动端交互键盘。

## 3. 统一通道调度器（UnifiedChannelOrchestrator）的核心实现

### 3.1 700ms 节流预览与 Telegram 限流平衡

在移动端即时通信网络中，Agent 的 token 增量生成速度（可达 50~150 tokens/s）远高于平台的 API 速率限制。Telegram 针对消息编辑（`editMessageText`）实施严格的单会话并发与频次限制，频繁编辑极易触发 HTTP 429 Retry-After。

`StreamPreviewController` 采用基于时间窗口的双缓冲节流设计：
1. **最小编辑间隔**：固定 700ms 节流窗口；
2. **内容差异校验**：如果当前渲染的 Markdown 内容与上一次已发送成功的内容无实质变化，跳过该帧；
3. **最终帧绝对交付**：流式结束后，无论节流计时器是否到期，强制刷新最终帧，确保输出不丢字、不截断；
4. **Typing 心跳保活**：在长文本推理或工具执行期间，后台每 4 秒维持一次 `sendChatAction('typing')`，消除用户的“死机焦虑”。

### 3.2 工具调用动态折叠与 4000 字符分块

复杂任务中，Agent 会产生大量终端执行、文件查找、代码替换等中间工具调用。若平铺在 Telegram 会话中，会迅速淹没正文结论。

调度器实现了工具调用的自适应折叠：
- 当工具开始执行时，进入内部 buffer；
- 转换为 HTML 规范的 `<blockquote expandable>...</blockquote>` 折叠块；
- 最终正文超出 Telegram 单条消息 4096 字符上限时，通过 `chunkTelegramMessage` 按照段落、代码块、句末标点边界安全切分为连续消息序列，防止 Markdown 标签不配对导致的富文本渲染崩溃。

### 3.3 崩溃自愈与跨重启状态机

守护进程更新升级或异常重启时，处于运行中的任务不能处于不可知的悬空状态。
`UnifiedChannelOrchestrator` 与 SQLite 存储层打通：
- 在系统启动时扫描处于 `running` 或 `queued` 的历史 Turn；
- 对未完成 Turn 标记为 `interrupted` 并向关联会话发送恢复通知；
- 释放旧的并发互斥锁，确保用户在服务重启后无需手动清空队列即可继续提问。

## 4. 典型引擎适配实战：Antigravity 适配器

Google Antigravity (`agy`) 是新一代面向复杂任务的深度智能体，其底层调用 CloudCode PA 接口与 Gemini 3.8/3.7/3.1 和 Claude 模型。将 Antigravity 接入 FoxClaw 涉及几个独特的挑战：

### 4.1 Token 预检与全自动刷新（Token Preflight）

Antigravity 的 OAuth Token 存储在 `~/.gemini/antigravity-cli/`。在真实环境中，Token 的有效寿命通常仅为 1 小时。若直接发起长任务 CLI 调用，过期的 Access Token 会导致数分钟后任务在模型层报错失败。

`AntigravityEngineAdapter` 引入了**预检与静默刷新机制**：
- 在每次执行 Turn 前，预先计算 access token 的剩余有效期；
- 若剩余时间少于 5 分钟，自动调用 Google OAuth 凭据端点执行静默刷新；
- 若刷新过程出现临时网络波动，执行回退并利用 `id_token` 中的账户哈希进行安全校验。

### 4.2 应对 Google 503 容量饱和与配额冷却轮换

在高峰期，大型推理模型可能频繁返回 `503 Service Unavailable` 或 `MODEL_CAPACITY_EXHAUSTED`。单次报错不应直接宣告任务失败。

我们在适配器中实现了两层自愈：
1. **指数退避重试**：针对瞬时容量饱和，适配器进行 1s、2s、4s 指数退避重试；
2. **配额超限自动轮换（Quota Cooldown Rotation）**：当当前 Google 账号遭遇真正的用量限额（ResourceExhausted）时，适配器自动将该账号标记为冷却态，无缝切换至候选池中的下一个可用账号，并在新账号下自动恢复执行。

### 4.3 彻底厘清配额展示：从时间误区到真实的 5h/7d 百分比

在早期的候选账号切换面板中，按钮前缀曾显示类似 `100|80|...` 的字符。这引发了一个严重的认知混淆：
“竖线前面的意义不是时间啊，为什么把百分比当时间展示？”

我们彻底重构了配额可观测模块：
- **真实指标定义**：Google PA API 返回的配额窗口为 `5 小时突发额度`（5h Window）与 `7 天长期额度`（7d Window），其返回值为 0~100 的**百分比数值（Remaining Percentage）**，而非倒计时或小时数；
- **显式 Badge 格式化**：在 `formatCandidateButtonPrefix` 中全面规范化为明确带百分号的徽标：`100%|80%|account_name`；
- **全链路感知**：在 `/auth` 列表、`/status` 面板与 `/setup` 概览中，统一以 `5h: 100% | 7d: 80%` 格式完整呈现，使开发者在手机上一眼看清各个候选账号的真实健康度。

## 6. 结语

FoxClaw 从一个面向 Codex 的个人小工具，迈出了走向通用 Agent 基础设施的关键一步。

统一通道调度器与可插拔引擎 SPI 的确立，不仅抹平了不同厂商 Agent 在命令行与网络协议上的差异，更让开发者无论面对哪一个大模型内核，都能在手机端拥有完全一致、稳定、丝滑的沉浸式控制体验。

AI 工具在不断演进，而沉淀在工作流最后一公里的这套运行保障底座，才是让 Agent 真正能够全天候陪伴人类工程师前行的坚实桥梁。
